# 隧道重启后经中转的回答被截断

0.11.0 发版前，CI 的 Ubuntu 上 `test_drop_during_command_preserves_session_output_and_does_not_replay` 连续 4 次超时失败，报 “ASGI callable returned without completing response” 和 “incomplete chunked read”。同样的提交在本机和 Windows CI 上都过。

查下来，问题出在 sse_starlette 的全局标志 `AppStatus.should_exit`：
- 它的关停监视器一旦看到某台 uvicorn 服务器的 `should_exit` 为真，就把这个全局标志置上，而且再不复位。我们停掉本机的 MCP 服务时，正好会这样。
- 标志置上以后，进程里所有 SSE 回答一开始就结束。
- 测试里，前一个用例停掉了它的本机服务；生产里，桌面端「重新连接」、断开再连、换中转地址，都会停掉一台本机服务再起一台。之后经中转的 MCP 调用都收不全，要重启 winhand 才好。
- 监视器每 0.5 秒看一次，停服务那一刻有没有看到，决定这次会不会出事，所以时有时无。

- 改动：`agent/src/winhand/relay_client.py` 的 `serve_local` 起本机服务前，先调 `_sse_survives_restarts()`：关掉 sse_starlette 的自动排空，并把 `AppStatus.should_exit` 复位。我们的关停（`_finish_local_server`）本来就会关连接、取消请求，用不着它。
- 验证：
  - 先把标志置上，再跑上面那个用例：修之前，复现了 CI 报错的原文；修之后通过；
  - 新用例 `test_a_restarted_tunnel_still_answers_whole_sse_responses`：去掉修复时失败，加上时通过；
  - 本机打印每个用例结束时的标志：3 次里有 2 次在第三个用例收尾时被置上，说明这种置上在正常测试里也会发生；
  - 用 CI 二分：0.10.2 和到第 4 轮的提交都过，从叫醒那个提交起失败。那个提交只是让时序变了，没有改到这条路径。
- codestable：已同步 `spec/waiting.md`。
