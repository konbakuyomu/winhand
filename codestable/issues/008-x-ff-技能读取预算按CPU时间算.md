# 技能读取预算按 CPU 时间算

主人问「前面 winhand 的技能问题解决了吗」，复测发现 0.15.0 还有一个缺陷：调用 `context()` 时，只要有别的调用同时在跑，地图就少列一批技能。线上看到的是 109 条，单独调用是 166 条，还提示「17 个技能文件夹太大没读全」。少的 56 条正好是 Codex 插件的技能。

原因是读取技能目录的预算按总时间算，2 秒。同时发出几个调用时，每个调用都被拖慢（单独 0.5 秒，4 个一起 3 秒），2 秒在读到 Codex 插件之前就用完了，那一批目录整个跳过，只留一句「太大」。Claude Code 本来就会并行发调用，所以这不是偶发。`skill(query=…)` 共用同一个预算，读不完时一个字都不提。

- 改动：
  - `agent/src/winhand/skills.py`：预算改成按调用线程自己的 CPU 时间算 2 秒，总时间只留 10 秒上限兜底；读不完的提示改成准确的话，`skill(query=…)` 的回答里也带上。
  - `agent/tests/test_skills.py`：三条新测试。用假时钟重现这次的事故，测预算怎么算，测读不完时 `context()` 和检索都会说。
  - `docs/rules-and-guards.md`、决定笔记、005 票的执行记录：改成新的说法。
- 验证：
  - 在主人电脑上，用同一份代码、同一台机器的真实技能目录（166 条）。每组同时发出 N 个 `context()`，在同一个进程里先跑 0.15.0 的原版，再换上修好的文件：

    | 同时调用数 | 原版：每个调用看到的技能数 | 修好后 |
    | --- | --- | --- |
    | 1 | 166 | 166 |
    | 4 | 161、129、163、129（每次不同，3 至 11 个文件夹被跳过） | 166、166、166、166 |
    | 6 | 109（17 个文件夹被跳过） | 166，一个都没跳 |

  - 第一次测（缓存是冷的）4 个一起时，原版得到 109、109、110、109，和线上看到的数字一样。
  - 单个调用的耗时没变：交替各跑 6 次，中位数原版 1.16 秒，修好后 1.18 秒。
  - 代价：同时调用多的时候，每个调用都要老实做完全部的活，4 个一起约 4 秒，6 个一起约 6.5 秒（原版靠跳过一批目录显得更快）。再多到总时间超过 10 秒，还是会读不完，但会说出来。
  - 新测试在旧代码上全部失败，在新代码上通过。
  - 检索在 8 个一起调用时，原版和修好后都能搜到 Codex 插件的技能，没有看到丢失。
- 发版：随 0.15.1 发出。
- codestable：已同步 `issues/005-o-技能分层发现与按需展示.md` 的执行记录，同一次提交里还改了 docs 目录的规则文档和 .agents 目录下技能那篇决定笔记。现状规格不用改，它没写这个数。

顺手发现：每个调用都重新读一遍全部技能，同时调用多时是重复劳动。缓存读到的清单能解决，但要管失效，这次没做。要做的话另开票。
