# 多 agent 协作台 talk

> 2026-11-21，云端 Claude 会话「多agent协作框架设计」里的讨论。参与者：用户、云端 Claude、本机 Codex（`gpt-6.2-astra`，推理强度 max，五轮）。
> 这是讨论记录，不是规格。结论以第 8 节和第 9 节为准；前面几节里被后来推翻的说法，在推翻处写明了。

---

## 1. 用户怎么起的头

用户给了六个做多 agent 合作的开源仓库：spacering-net/codeg、Kuddev/pebrel、useLexora/Lexora、yicheng47/runner、TreeX-xx/JanusX、keli-wen/cospan。要求从中吸取经验，做一个多 agent 合作的框架。原话里的几个要点：

- 彻底解耦。winhand 本质上只是连接器，以后云端可能不是 Claude（准备买 Gemini Pro 会员），相当于云端 AI 经连接器和本地 AI 联动。
- 不限一个渠道只出一个模型。例子：云端 Claude 同时有 4 个对话在跑，彼此独立；希望它们能在聊天室里互相交流、讨论。
- 担心：会不会影响彼此的独立、造成上下文污染；主调度怎么处理，总有一个模型得和用户交互。
- 用户说自己对这类架构不熟，要 Claude 和本地的 6.2 astra 讨论。后来又明确：讨论和审查都用 `gpt-6.2-astra`、max。

用户提到的「本地 AI hermess」：电脑上没有 `hermes` 命令，指什么**还没问清**。

## 2. 先查到的现状

讨论前从仓库和电脑上核实的事实，后面每一轮都以它们为前提。

**看板仓已有一条相关的线。** dev-board 的 Epic `001-o-dispatch-v3`（状态 draft）：票、台账、gate、排队道、patrol，一个云端 Claude 会话当总调度，执行者按配置可换。它定过一条原则：状态只放电脑上的文件，消息和事件只用来叫醒。它用 GitHub 私有仓的 PR 评论叫醒云端会话，实测 14 秒，但 38 张票全带了 `--no-inbox` 没用它（见 `.agents/notes/implemented/feature/2026-11-17-wake-through-wait-links.md` 的「Alternatives」）。

**云端 Claude 会话的硬限制（那条线上实测的）：**

- 只能被这几样叫醒：用户发消息；自己沙箱里的后台命令结束（最长 2 小时）；订阅的 PR 事件；别的会话发消息；定时任务。
- 正在干活的会话收不到即时叫醒，事件排队到这一轮结束。
- 会话间发消息、开会话在自动模式下被分类器拒过，不保证送达。
- 醒一次要把 30–60 万 token 的上下文重读一遍。

**winhand 已有的两样能力：**

- 等待链接：云端沙箱后台 curl 一个电脑签发的地址，条件满足命令就结束，会话被叫醒。条件有四种，其中一种是「某个文件出现或改动」（`agent/src/winhand/transfer.py` 的 `issue_wait`）。
- 本机 MCP 转发：电脑上任何 MCP 服务可以经 `mcp_call` 调用，也可以成为独立地址 `/pc/<电脑>/mcp/<服务>`（`docs/local-mcp.md`）。

**本机：** Codex CLI 0.171.0，默认模型 `gpt-6.2-astra`；`dsh`（DeepSeek Harness）已装；`gemini`、`agy` 未装。

## 3. 六个项目读下来的结论

六个只读子代理各读一仓的源码（浅克隆，只读不运行）。

| 项目 | 许可证 | 它是什么 | 值得借的 |
|---|---|---|---|
| runner | MIT | 本机桌面程序，多个 CLI agent 各占一个终端，共用一条消息流。六个里唯一的对等聊天 | 只追加的事件日志是唯一真相，每人的信箱是它的视图；叫醒只往终端打一行指针，正文自己去读，带累计已读位置；它把 lead 角色删了，改成「关联对话」只收「需要你、失败、收敛」三种通知 |
| Lexora | AGPL-3.0 | 进程内的 agent 树，不驱动外部 CLI | 消息分种类，结果和提问叫醒收件人，进度不叫醒；提问写明问上级还是问人；投递台账（待投、已收、已用、被拒）；委派默认隔离上下文；同级只能发信不能互等 |
| JanusX | MIT，核心引擎无源码 | 一个协调者加若干工人，工人互相看不见 | 严格的交回格式（就绪、提问、失败，带检查项和证据）；「报告不是授权」，每次派活要引用一条人的输入；结果不明绝不自动重发；圆桌讨论有固定阶段 |
| codeg | Apache-2.0 | 约 20 种 CLI 的统一界面，全走 ACP，只有父派子 | 批量长等待，任一任务结束或卡在等人就返回；子任务卡住往上报一次；委派深度上限 |
| pebrel | GPL-3.0 | 带 agent 感知的终端复用器 | 按「身份加代数」寻址，重启后的新会话不继承发给旧会话的活；每个 agent 一个 worktree |
| cospan | MIT | 单向委派工具（发、等、取结果） | 每种 CLI 一个驱动；带超时的等待；限长的进度快照；续用工人的原会话 |

横向两条：

- **六个项目没有一个支持云端 agent 加入。** 全部单机，靠握住本机进程或往本机终端打字来叫醒。云端会话只能发工具调用，这条路走不通。
- 只有 runner 做了对等聊天，而且它也把自由聊天收得很紧。其余五个都是上级派活、下级交回。

Lexora 和 pebrel 的许可证有传染性，只借概念，不抄代码。

## 4. 第一轮：astra 的独立意见

Claude 只给事实和八个分叉，没给自己的倾向。两边独立得出同一主干：

- 协作层是独立服务，不做进 winhand，不拿 GitHub 当总线。
- 「聊天室」做成成员主动进入、按议题阅读的房间，底层是定向信箱加线程。不做默认全员收全文的自由群聊。
- 叫醒只送指针；收件人**先签发等待，再补读一遍信箱**，空了才挂等。顺序不能反，否则挂等前到的信不会触发。
- 调度规则写在程序里，每个议题一个可移交的对人联系人，默认是用户发起它的那个对话。
- 凡是决定谁能看材料、谁能产生实际动作、何时必须停的规则，由代码执行；说话方式放提示词。

Claude 被纠正的三处，以 astra 的为准：

- **顺序。** Claude 原来把资源认领排第一。astra 把定向信箱排第一、认领第二，更贴合用户说的「互相交流讨论」。
- **独立性挡不住的部分。** 一段话只要被某个会话读入，就会影响它之后的回答。所以需要保持独立判断的主线不进议题，另开一次性讨论会话，只把结论带回。
- **资料外发。** 同一个房间里有不同厂商的模型，等于把材料交给不同接收方。Claude 第一遍漏了这一条。

astra 另提三个要命的问题：动作成功但回执丢了；认领过期但旧进程还活着；材料进了另一个供应商的上下文就撤不回。

## 5. 第二轮：astra 审合并方案

Claude 交了合并方案 v0.1 和七处分歧。astra 的裁决：

- **身份。** 赞成自助加入，收回「每个对话都要人工配对」。人工核对只放在三处：首次绑定既有职责、敏感项目准入、有争议的接班。
- **状态卡。** 保留按需查询的卡，但从台账、认领记录生成，不让每个成员手工维护一份小事实库。
- **待决清单。** 需要，一个能找回所有未决问题的查询就够。每个问题有编号和版本。业务决定和动作授权要分开。
- **人的来源。** 人和 agent 都能跑本机命令行，「命令在本机执行」不能证明是人写的。
- **资料外发。** 只按项目和成员种类准入不够。要核「材料、实际接收方、允许动作」三项，衍生的摘要继承来源的限制。它还查到一处文档差异：早期规矩禁止 Codex 接触板子文件，11-14 已放宽为可只读、不可改工程，收集的资料仍不给。
- **和分发 v3 衔接。** 先改「开不了 PR 就不派」这条派单前提；把「当前该接结果的人」和票面负责人分开；只迁作业结果还不能退役 GitHub 信箱，巡检告警要分别验过。

这一轮里关于入口的裁决（P0 经现有 `mcp_call` 进协作台）**后来作废**，见第 8 节。它读源码得到的两条事实仍然有效：独立地址 `/mcp/<服务>` 那条路不经过守卫；winhand 的调用历史对所有会话可见，凭据和私信正文可能从那里漏出。

## 6. 用户补充：拿硬件工作流当实例，要统一前端，本地模型也要参与

用户说：可以先观察正在跑的硬件工作流，它很笨重原始；用户没有统一的前端界面看各线程的进度和交互；以后还想让本地的 DeepSeek、ChatGPT、Gemini 也参与讨论，所以需要一个新工具。

Claude 只读观察到的现状（2026-11-21）：

| 观察项 | 现状 |
|---|---|
| 形态 | 一个「评估和调度」云端会话当枢纽，一件事开一个子会话，做完交回 |
| 规模 | 当天开了 40 多个子会话，分设计师、执行者、验收、合并、探路 |
| 枢纽的花费 | 约 17 小时 205 美元，缓存读 2.06 亿 token |
| 交接 | 子会话把报告写到暂存目录的 `report.md`，再发一句「已交回」 |
| 枢纽的账本 | 53 个文件、480 KB；决定日志追加到第 27 号 |
| 用户怎么看 | claude.ai 会话列表（大半未读）、生成的工作流页面、每天采集一次的看板卡片 |
| 等用户的事 | 一个设计师会话在等用户定一项豁免、给一份连接器规格书，只写在那个会话的摘要里 |

第三轮 astra 的意见：

- **第一步接「设计师停下等人」这个动作。** 验收标准：用户打开一页就知道哪位设计师在等哪两件事，答完一件能看到对方收妥，另一件仍留在首页。
- **议题跟着交付物或待裁问题走。** 同一件事的执行、返修、验收可以换会话，仍归同一议题。否则 40 多个未读对话只会变成 40 多行待点记录。
- **「就绪」显示成「已交回，待复核」。** 完成线、板文件、报告正文、独立验收、正式决定留在原项目。
- **本地模型分两类成员。** 带工具的 agent（Codex、dsh、以后的 Gemini 命令行）和纯讨论者（只调模型接口）。驱动要能识别一次运行、查它的状态、安全地结束或接回它。
- **圆桌默认一轮。** 点名两位最相关的成员，同一版材料独立作答，答案先封存。一致就当轮收束；只有会改变决定的分歧才交给一人复核一次。参加过设计讨论的不能再当这块板的独立验收者。
- **P1 只留三样：** 最小结构化交回、能闭环的待办清单、统一页面。
- **三个上线阻断项：** 误认本人；扩大资料受众；把协作回执误画成真实完成（执行者报就绪就亮「完成」）。

这一轮 astra 选的「前端只做本机网页」**后来作废**，见第 7 节。它指出的洞仍然有效：获批操作浏览器的 agent 也能点已登录的网页，所以网页登录不能证明是本人。

## 7. 用户答复，和第四轮

用户对合并方案的四个问题答复：

- 方向：其他都认同。前端网页要能部署在 Cloudflare Worker 或自己服务器上，因为很多时候是手机在查看和交互。
- 代码放哪：新建独立私有仓。
- P0 穿刺：讨论落盘后就做。
- 本人确认：先按 winhand 自己的确认窗口设计。

第四轮 astra 在「协作台仍经 winhand 进入」的前提下选了：主账留电脑，Worker 上放获准的快照加一个答复待取箱，手机入口用 Cloudflare Access。它同时写明改判条件：验收一旦变成「电脑断开时云端会话仍须据此继续工作」，就把主账搬到服务器。这个前提在第 8 节被用户改掉，**存储的结论以第 8 节为准**。

第四轮里仍然有效的：

- 手机验收提前到穿刺的第二步。
- 手机页面按项目显式开启可见范围，每个项目只选一档：不发布、可看摘要、可看并答复。默认不出现真实板名、绝对路径、命令、附件、原始报告和日志、私信正文。
- 手机上要让用户明确看见「答复已收到，正在等电脑处理」，区分远端已收和原任务已采纳。
- 本人确认先按 winhand 确认窗口定一套规则，手机通行密钥作为同一规则的第二种证明。首把密钥的登记要在可信的本机环节确认，已登录网页没有抢先登记的权限。

## 8. 用户再补充，和第五轮：最终以这一节为准

用户又说了两件事：

1. **日常交互。** 用户习惯在网页端或本地 harness 里直接和 AI 聊天，不想专门到那个网页上打字。希望 AI 自己也能发起讨论：用户的 AI 经连接器连上协作台，AI 自己发起，用户上网页是直观地看。协作台后台要调度各家 AI。从网页直接发起讨论组也行。
2. **入口。** 不在 winhand 里加协作台的入口，单独做成一个 MCP，保证解耦和通用。

第 2 件改了前面的前提：云端对话成了直接往协作台写入的一方。Claude 提出改选「主账在服务端」，astra 第五轮同意并改判。

**已确认（两位一致，以此为准）：**

- **主账在协作台服务端。** 原则修订为：协作事实由协作台裁定，项目事实由原项目裁定。议题、成员、预算、投递、业务答复归协作台；票、板账、报告正文、gate、设备实际占用归电脑或仓库。原规则防的是「把可能丢的会话消息当事实」，这条理由不变。
- **三块组成。**
  - 协作台服务端：账本、规则、MCP 入口（自己的 OAuth）、网页和手机页、按已读序号的等待接口。astra 建议首站放自有服务器，独立服务、独立数据库。
  - 本机执行器：跑在有命令行模型的电脑上，主动连出。只领「请指定成员在限定范围内开一轮」的请求，用驱动跑 Codex、dsh、以后的 Gemini，交回结果。本机资源占用由实际控制入口确认。
  - 各家 AI：经连接器直连。winhand 不在这条路上。
- **本机执行器和 winhand 的关系。** 在这台电脑上优先复用 winhand 的后台任务、按名注入密钥、守卫和确认窗口，做成可替换的本机实现。完全另写会丢掉已有的超时清理、退出码、恢复记录和主人规则。
- **AI 发起讨论。** 一次工具调用给出议题、点名成员、材料引用、形式和预算；立即返回议题编号、每位受邀者的状态、预留额度、截止时间。发起的对话默认是联系人，结果回到它那里。
- **花费和循环。** 这次调用只能动用用户预先授予的额度。费用归实际调用的账号，同时占发起项目的预算，启动前原子预留。受邀的这一轮只能回答本题，无权再派。跨议题另设账户总上限。
- **长会话和新会话区别对待。** 背着几十万上下文的云端长会话，默认下次自然开轮再取信；只有它登记了待命、额度覆盖重读成本时才自动叫醒。只要一个独立意见时，优先开干净、限时的新会话。
- **用户在哪交互。** 用户继续在原对话里聊天。一件待决的事只登记一次、只由一个联系人提问；入账时手机页就可见。在哪看到就在哪答，服务端按同一问题编号和版本采纳一次，各处同时消项。
- **来源分三档。** agent 转述、已登录网页、本人确认。对话里的 AI 转述用户的话，记为 agent 转述。
- **纯讨论者先放本机执行器跑。** 模型凭据留在电脑，协作台主服务不持有付费模型的凭据。
- **首版不做：** 专门让用户重聊一遍的聊天框；受邀者再拉人；默认全员互评；电脑和服务器双主回写；通用应用隧道；自建 WebSocket 中转。

**被这一节推翻的旧说法：**

- 「P0 经 winhand 的 `mcp_call` 进协作台」「穿刺阶段 winhand 不改代码就能跑」：入口改成独立 MCP，这条路不走了。
- 「主存在电脑」「前端只做本机网页」：改成主账在服务端，网页手机优先。
- 「用 winhand 的文件等待叫醒云端会话」：改成协作台自己的等待接口。

## 9. 穿刺怎么做（两位一致）

1. **定向叫醒。** 最小鉴权、收件隔离、幂等、一次叫醒上限先在本机过关，再部署公开样题入口。同账号两个已加载连接器的真实云端对话分别登记、挂等，只向其中一个投递。验收：目标对话无人催促实际开一轮；旁观的保持静默；彼此读不到对方私信；等待接口只回状态，正文要重新鉴权去读。
2. **复现这次讨论。** 用户在 A 对话提问，A 一次调用点名 Codex，本机执行器只开一轮，结果回到 A，A 在原对话里向用户讲出结论。只在服务器上看见 Codex 的结果不算过。
3. **真手机。** 让测试执行器离线，手机提交一条普通业务答复，协作账立即采纳有效版本，原对话能读到同一收据。

astra 判断最可能卡住自动闭环的一点：平台能从公网调用 MCP，和那个对话自己的沙箱能访问新入口、挂住后台命令、结束后得到新一轮，是两条路径。后一条在新入口上**未核实**。失败时定向收信和主动拉取仍可用，但不能宣称结果会自动回到原对话。

## 10. 候选质量目标（非承诺）

- 可靠性：已提交的信在挂等交界、休眠恢复、服务重启后不丢；结果不明的调用不自动重开。
- 信息安全性：受限项目的正文不到服务器；另一个会话看不到可复用的凭据和私信正文；公网讨论权不能变成本机执行权。
- 性能效率：不为进度和闲聊开轮；记录多少次叫醒实际解决了问题。
- 兼容性：换一家云端模型或本机命令行，只加一个驱动或一个连接器配置。
