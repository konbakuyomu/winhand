# 第 1 轮小修（0.7.4）

## 做成以后是什么样

- `fs_read` 读 PDF、Word、PPT、Excel 时，Claude Code 里的模型能看到正文。
- 反复轮询 `job_status` 时，只回新的东西：
  - 启动命令、日志路径只在第一次回；
  - stderr 只回上次之后新写的部分；
  - 没有新输出时，回复很短。
- 开场说明告诉 AI 三件事：服务器用 `remote_run`；拿文件用 `fs_send` 一次取回；写提交信息用 `git commit -F -` 加 `stdin`。
- `run-N` 编号在 winhand 重启后接着往下编，不再重复。每个 `run` 一开始就有 id：掉线后 `history()` 里能看到它，`job_status` 也能接着等。
- 几个小参数不再白白报错：
  - `fs_search` 的路径不存在时，说清楚“没有这个路径”；
  - 认 `ocr` / `screenshot` 的 `area`；
  - 和 `edits` 一致的 `old/new` 不报错；
  - 什么都不改的编辑跳过并注明；
  - `command` 和 `shell` 写的是同一个解释器时不报错；
  - `job_status` 的 id 写成 JSON 字符串时也能解析。

**范围：** 只动 agent。不改中转，不改桌面端，不改任何现有参数的含义。

## 为什么现在做 / 当前坏在哪

依据 `docs/reviews/2026-11-01-usage-review.md`：

- **读文档丢正文**：`media_result()` 同时返回结构化的概况（facts）和正文。Claude Code 只把结构化部分交给模型，正文没交过去。
  - 2026-11-01 复现：读 289 页的 PDF，只回 `{"type":"pdf","pages":289,...}`。
  - 77 次读文档里，有 24 次 AI 紧接着自己写脚本抽文字。
- **轮询回复重复**：
  - 启动命令占 `job_status` 回复字节的 35–49%；
  - 直接运行的程序每次都回 stderr 末尾 6 KB；
  - 0.7.0 之后 `job_status` 占全部调用的 16.6%。
- **开场说明没提 `remote_run`**：0.7.0 之后，`run` 直接调 ssh 124 次，`remote_run` 0 次。`fs_send` 只用过 3 次。
- **`run-N` 编号重复**：重启后从 1 重新编号，出现过同一个 `run-92` 跨 5 天。
  - 掉线后 `history()` 只显示 `running`，不给 id。
  - AI 猜了个 `run-100` 去等，回来的是“no running command”。

## 方案与实现安排

1. **读文档**：结构化部分加上 `text`。内容块仍然是“概况 JSON + 正文 + 图片”，这样只显示内容块的客户端不会看到两遍正文。
2. **轮询瘦身**：在 `tools_desktop` 里给每次回复做标记，记下（任务 id，游标）→ 已经回过的 stderr 字节数。
   - 同一个游标再来时：去掉 `command`、`log_file`、`started`、`elevated`；stderr 只回标记之后的部分；
   - 任务结束时照常给全部字段；
   - 给了 `tail` 时照常回 stderr 末尾。
   - 标记只在内存里保存，数量有上限，任务结束就清掉。
3. **开场说明**：加上述三句；同时压缩全屏程序、`sys_info` 两段，保证总长不超过 4096，已存密钥的名字仍能多列几个。
4. **`run` 编号**：
   - 计数器存在 `~/.winhand/state/run-counter`，每次分配时读、加一、写回（有锁，原子替换）。
   - 进程一启动就登记到 `_running`。
   - `history` 中间件开放一个“当前调用”的上下文，`run` 拿到 id 后写进这条记录。
   - 找不到的 id 如果比本次启动的第一个编号还小，就说明是“winhand 重启前的命令”。
5. **小参数**：照上面“做成以后”逐项实现，每项一个测试。

## 验证

- 新增测试：

## 执行记录

2026-11-01，分支 `claude/sweet-fermat-rqo6gd`，版本号改为 0.7.4（`agent/pyproject.toml`、`agent/src/winhand/__init__.py`、`agent/uv.lock`）：

1. **读文档**：
   - `tools_desktop.media_result()` 加 `structured_extra`，内容只进结构化部分；
   - `server.py` 的文档分支把正文放进去：`structured_content["text"]`；
   - 概况块仍然只有概况，只显示内容块的客户端不会看到两遍正文。
2. **轮询瘦身**：`tools_desktop.trim_repeat()` 按（任务 id，游标）记标记，值是交出这个游标时的 stderr 大小。
   - 从同一个游标接着问时：去掉 `command`、`log_file`、`started`、`elevated`；stderr 只留标记之后的部分；
   - 任务结束时照常给全部字段；给了 `tail` 时照常回 stderr 末尾。
   - 与方案的偏差：原想“同一游标取最小值”，但只写 stderr 的任务（Codex）游标一直不动，这样会反复回同一段 stderr，所以改成记最新值。代价是两个调用方用同一游标轮询同一任务时，可能各自漏看对方已经看过的行，用 `tail` 可以补看。
   - 另外，`job_status` 的 id 写成 JSON 字符串、或用逗号、空格分隔时也能解析（`_job_ids`）。
3. **开场说明**：
   - `run` 的第一个示例换成 `git commit -F -` 加 `stdin`；
   - 加一条 `remote_run`；文件一条加上 `fs_send(path)`；
   - 压缩交互会话和 `sys_info` 两段，去掉全屏程序一段（完整版 `help()` 里还有）。
   - 结果：总长 3999；12 个已存密钥名全部列得下，原来只列 9 个。
   - 完整版 `help()` 补了同样三点。
4. **`run` 编号**：
   - 编号来自 `proc._next_run_id()`，计数器在 `~/.winhand/run-counter`，原子替换写回。
   - 程序一启动就登记到 `_running`；结束的保留最近 20 个（`_forget_finished`）。
   - `history.note_current()` 把 `run_id` 写进在途的那条记录。
   - 找不到的编号如果小于本次启动的第一个编号，就说明“重启前跑的，输出已经没了，`history()` 里有它的结果”。
5. **小参数**：
   - `fs_search` 的路径不存在时报“no such file or folder”，原来是 WinError 267；
   - `ocr`、`screenshot`、`fs_read` 认 `area`，当作 `region`；
   - `fs_edit` 里与某处 `edits` 相同的 `old/new` 不再报错；
   - 新旧文本一样的修改跳过并注明；全部一样时不写文件；
   - `run` 的 `command` 和 `shell` 是同一个解释器时（`python` 加 `python`、venv 的 `python.exe` 加 `python`）照常执行。
6. **方案里有、但不需要再改的两项**：
   - `fs_list` 指向文件已经在 0.7.0 处理了；
   - `fs_search` 的 `context` 超过 20 已由参数容错中间件截到 20。
   - 调用日志里 0.7.0 之后这两类报错都没有再出现。
