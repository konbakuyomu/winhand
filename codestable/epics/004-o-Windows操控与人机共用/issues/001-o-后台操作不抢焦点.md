# 后台操作不抢焦点：两招守卫与回归

## 做成以后是什么样

AI 通过 `ui` 对一个窗口做控件操作时，不管主人在不在打字，前台都不动，也不会多出任何系统输入。控件操作包括点击、切换、选择、展开、写值、滚动到可见。两招守卫是：

- **不可激活**：动作期间给目标的顶层窗口加 `WS_EX_NOACTIVATE`，做完只去掉这一位；
- **临时禁用**：对 XAML、UWP、WinUI、Chromium、Electron 宿主，在模式调用期间对顶层窗口 `EnableWindow(FALSE)`，调完恢复原来的启用状态。

`window` 的最小化、还原、最大化、移动，在目标不是前台窗口时也不把它切到前台。`window(action="focus")` 本来就是要切前台，不变。

**范围：**
- 包含：
  - `uia.act` 的各个动作；
  - `desktop.native_act`（投递 `BM_CLICK`、`WM_SETTEXT`）；
  - `_ui_act` 里走 PowerShell 的 UIA 退路；
  - `uia.scroll_into_view`；
  - `window` 的这四个动作；
  - WPF 宿主的识别；
  - 守卫在各种结束路径上的还原；
  - 回归测试。
- 不包含：
  - 让后台动作不再等主人停手（第 2 张票）；
  - `_ui_act` 找不到控件模式时退回前台真点（第 3 张票和之后的工具契约切片）；
  - `input`、`ocr` 的点击和按键：它们本来就是往前台送输入；
  - 控制会话和信号。

## 为什么现在做

- **主人打字时会被抢。** 2026-11-24 在主人电脑上做了配对实测，winhand 0.13.0 的源码，直接调 `uia.snapshot` 和 `uia.act`：
  - 12 轮里，每轮写字符映射表的值时抢一次焦点，点计算器的「清除」时抢一次，共 24 次；
  - 「清除」当时是灰的，点击被拒，焦点照样被抢；
  - 主人打的数字进了 AI 的窗口（「0winhand 第 1 轮」，计算器结果变成 17、13、93）；
  - 第一次抢之前，系统里多了一次注入键 VK 0xB9，winhand 的代码没发过这个键。
- **主人没打字时也抢。** 48 个动作里 15 次。
- **加上两招就不抢了。** Python 原型：主人没打字时 48 个动作 0 次，打字时 72 个动作 0 次，注入 0，结果全对。

这是后面所有「人机共用」的前提：不先挡住抢焦点，第 2 张票放开等待以后，AI 就会抢主人的输入。

## 现状怎么工作

`ui` 的动作 → `tools_desktop._ui_act`：先找控件，再按下面的顺序走，前面不行才走后面：

1. 经典按钮投递 `BM_CLICK`；
2. `uia.act` 调 UIA 模式；
3. PowerShell 脚本的 UIA；
4. `native_act` 发 `WM_SETTEXT`；
5. 最后切到前台真点一下。

整个动作套在 `presence.acting()` 里：主人在用电脑就先等。没有任何地方阻止目标窗口在动作期间被激活。

`window` 的还原、最大化、移动用 `ShowWindow(SW_RESTORE)`、`ShowWindow(SW_MAXIMIZE)`，这两个调用本身会激活窗口。

## 方案与实现安排

取舍见 [决定笔记](../../../../.agents/notes/proposed/architecture/2026-11-24-windows-control-own-backend.md) 的「第一步」。原型是主人电脑上 `~/.winhand/scratch/cua-trial/paired.py` 里的 `class guard`。要点：

- **一个上下文管理器套住每次后台动作**，放在 `desktop` 里，`tools_desktop` 和 `uia` 的调用点都用它，不在各处各写一遍。
  - 按目标的顶层窗口工作（`GetAncestor(GA_ROOT)`）。
  - 先加 `WS_EX_NOACTIVATE`，读回确认加上了，以后只去掉这一位。
  - 宿主类名命中下面这些时，再加 `EnableWindow(FALSE)`：`ApplicationFrameWindow`、`Windows.UI.Core.CoreWindow`、`WinUIDesktopWin32WindowClass`、`Chrome_WidgetWin_*`。用 `EnableWindow` 的返回值记下原来是否禁用，还原时按原状态恢复。
- **超时**：`uia.call` 超时后，工作线程可能还在程序的处理函数里。
  - 守卫要等那次调用真正返回再撤，可以挂在 future 完成时；
  - 同时设上限，超过上限就还原窗口，并在回复里写明「已发送、程序还没处理完」，不能让窗口一直是灰的。
  - 上限取多少，实现时按 `INVOKE_WAIT_S` 定。
- **不加守卫的情况**：
  - 窗口在别的虚拟桌面上：用 `IVirtualDesktopManager.IsWindowOnCurrentVirtualDesktop` 判断，判断不了就照常加；
  - 样式加不上：以管理员身份运行的窗口会被 UIPI 拦下，现在本来就拒绝。
- **WPF**：顶层窗口类名以 `HwndWrapper[` 开头的，认作 WPF。守卫照套，但结果里标出「WPF 可能抢焦点」，供第 2 张票决定这类窗口继续让路。
- **`window` 动作**：
  - 还原用 `SW_SHOWNOACTIVATE`；
  - 移动用 `SetWindowPlacement` 加 `SWP_NOACTIVATE`，不先 `SW_RESTORE`；
  - 最小化用 `SW_SHOWMINNOACTIVE`；
  - 最大化在守卫里做，实测确认不激活；做不到就写明这一项会切前台。
- **崩溃恢复**：winhand 在守卫期间崩溃，目标窗口会停在禁用状态。实现时定一种办法：启动时还原上次记下的窗口，或者只在说明里写清怎么恢复。定下的写进本票执行记录。

**质量承诺：**
- **交互能力**：主人在前台打字时，后台控件动作不改变前台、不注入键鼠，主人的字逐字不变。来源：Epic 质量约束、主人要求。
- **可靠性（可恢复性）**：正常、被拒、异常、超时、急停之后，目标窗口的启用状态和扩展样式都和动作前一样。

## 验证

- **Linux 单测**：宿主类名判断；守卫在正常、异常、超时这几条路上加和撤的顺序。用假的 user32 测。
- **Windows 场景测试**（`agent/tests/test_windows_scenarios.py`，CI 的 Windows 任务里跑）：测试自己开一个经典窗口，带编辑框和按钮，从另一个窗口在前台的状态开始，对它写值、点按钮。
  - 前台不变；
  - 窗口的样式和启用状态还原。
  - CI 上没有商店程序，UWP 只在主人电脑上测。
- **主人电脑上的「主人输入不受影响」实测**：
  - 主人在记事本里打已知数字，40 秒以上；
  - AI 通过 winhand 的 `ui`（装上新版，或者从检出直接跑）对字符映射表写值，对计算器点包括灰按钮在内的按钮；
  - 要求：前台变化 0（每 5 毫秒轮询），注入 0（低级钩子带正对照），记事本内容逐字一致，AI 窗口里没有串进来的字符。
  - 第 2 张票还没做时，`ui` 会先等主人停手，所以这项实测要临时关掉 `yield_to_owner` 来跑，跑完恢复。
- **补测**：一个 Chromium 或 Electron 窗口（独立配置的 Chrome，或主人同意的某个程序）。

## 执行记录

**2026-11-24：实现。** Codex 在主人电脑的工作树里写，我审查，按审查意见续跑一次。

- `desktop.py`：
  - `host_kind()` 按顶层窗口类名分成 xaml、chromium、wpf、win32 四类。
  - `BackgroundGuard` 和上下文管理器 `background()`：
    - 给顶层窗口加 `WS_EX_NOACTIVATE`，加完读回确认；撤的时候只清这一位。
    - xaml、chromium 宿主再 `EnableWindow(FALSE)`，按原状态恢复。
    - `release()` 加锁，重复调用只生效一次。
    - 窗口在别的虚拟桌面上时，不加样式（`IVirtualDesktopManager`，COM 失败时按「在当前桌面」处理）。
  - `_window_act`：目标不是前台窗口时，最小化用 `SW_SHOWMINNOACTIVE`；还原，以及移动前的还原，用 `SetWindowPlacement` 加 `SW_SHOWNOACTIVATE`；最大化套守卫。目标是前台窗口时保持原写法。
- `uia.py`：
  - `act()` 和 `scroll_into_view()` 接受 `hwnd`，经 `_guarded()` 套守卫。
  - 调用超时（`NoAnswer`）时，守卫等那次调用真正返回再撤，最多 `GUARD_CAP_S` = 30 秒。
  - `call()` 把 future 挂在 `NoAnswer` 上；`explain()` 把 COM 错误转成 `NoAnswer` 时，也挂上。
- `tools_desktop.py` 的 `_ui_act`：
  - 投递点击、`uia.act`、PowerShell 退路、`WM_SETTEXT`、滚动到可见，五处都套守卫；
  - 前台真点退路没动；
  - 目标是 WPF 程序时，结果里加 `focus_note`。
- **和方案的出入**：
  - 样式加不上时，不报错，照常往下做。Codex 第一版在这里抛错，在 Windows 上把用假句柄的测试都弄坏了。票里定的是：加不上的只有以管理员身份运行的窗口，现有规则本来就拒绝。
  - 崩溃恢复还没做，验收后再定。
- **测试**：
  - 新增 `tests/test_background_guard.py`（14 项）：类名分类；只撤自己加的；原来禁用的仍禁用；原有的 `WS_EX_NOACTIVATE` 不撤；`release` 只生效一次；超时时等调用结束再撤。
  - 旧测试里替换 `uia.act`、`scroll_into_view` 的假函数补上 `hwnd` 参数（`test_desktop_redundancy.py`、`test_review_round4.py`、`test_approvals.py`）。
  - `tests/test_windows_scenarios.py` 加了「记事本在前台时操作测试窗口，前台不变、样式还原」的场景，由 CI 的 Windows 任务跑。在主人电脑上不跑：它会在主人的桌面上开窗口、抢前台。
- **结果**：
  - Linux 全量 1001 过、87 跳过；`ruff check`、`ruff format --check` 都通过。
  - 主人电脑上，桌面相关的 4 个测试文件 155 过、1 败。失败的那个走完整的 `ui` 工具，碰上主人正在动鼠标，让路等满 10 秒后放弃，单独重跑通过。改动前的基线也有 5 个这样的失败。
- **验收**：主人电脑上的「主人输入不受影响」实测正在进行，脚本是主人电脑上的 `~/.winhand/scratch/cua-trial/accept001.py`，走 `_ui_act` 的真实路径。
