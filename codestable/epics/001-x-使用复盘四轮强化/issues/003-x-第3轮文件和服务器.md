# 第 3 轮（0.9.0）：文件进出电脑与服务器

## 做成以后是什么样

- **多个文件或整个文件夹一次传。**
  - 上传：zip 自动解开，并逐个核对 sha256。
  - 下载：按目录或通配打包。
  - 大文件分片上传，每片 30 秒内传完。
  - WinHand 有自己的暂存目录，用户清理 `%TEMP%` 时不会丢。
- **文件工具一次处理多个目标。**
  - `fs_read(paths=[…])`；`fs_search` 一次多个查询。
  - `fs_edit` 跨文件改：要么全成，要么全不改，可以先预演。
  - 原文对不上时，给出最接近的原文和差异；新内容里多出 `\"` 时提醒。
- `context()` 有简要模式：技能只列名字；内容没变时只说“没变”。
- **`remote_run` 补齐。**
  - 加 `secrets=`；能拷文件；能开端口转发（后台运行）；自动遮挡网址里的 `user:password`。
  - `run` 里直接调 ssh/scp 时，提示改用 `remote_run`。

## 为什么现在做

- 57 批一次传 4 个以上的文件，共 349 个，多半靠打 zip。
- 超过约 10 MB 的上传在 30 秒左右报 502。有一次切片上传花了约 17 分钟、69 次调用。
- 连读多个文件的批次有 884 批；自写替换脚本改 15 张卡，首次运行就出错 6 次。
- `context()` 每次 25–45 KB。
- 运维会话里，ssh 全部走 `run`，密钥是从管道塞进去的。

见 `docs/reviews/2026-11-01-usage-review.md` 第四节 5、6、7。

## 执行记录

2026-11-01，分支 `claude/sweet-fermat-rqo6gd`，版本号改为 0.9.0。

文件进出电脑的几处取舍（边打包边下载、每片一个链接、全有或全无的解开、暂存目录不清理）和被否掉的做法，见 `.agents/notes/implemented/feature/2026-11-01-files-through-one-link.md`。

1. **文件夹和多个文件一次传**（新模块 `agent/src/winhand/bundle.py`；`transfer.py`）：
   - **下载。** `fs_download_url` 收文件夹或 `paths=[…]`，可加 `include`、`exclude`，按文件夹下的相对路径或名字匹配。边打包边下载，电脑上不留临时 zip，所以没有事先算好的 sha256，回复里说明用 `unzip -t` 检查。
   - **读规则逐个文件判断。** 用 `guard.PathCheck`：从 `fs_search` 的结果过滤里抽出来，搜索、下载、解开三处共用。被保护的文件不放进 zip，回复里列出名字。链接和联接点不跟进去。打包途中读不了的文件，记在 zip 里的 `winhand-errors.txt`。
   - **上传后解开。** `fs_upload_url(path=文件夹, extract=true)`，收 zip 或 tar。先查完再写，任何一项不过就整包拒收，一个文件也不写：
     - 不安全的名字：绝对路径、`..`、盘符、Windows 设备名、末尾带点或空格、带 `:`；
     - 包里有链接或设备文件；
     - 会经文件夹里已有的链接写到外面（空文件夹条目也查）；
     - 在 Windows 上会撞名：只差大小写，或文件与文件夹同名；
     - 写规则保护的文件，包括桌面审批文件；
     - 已存在的文件，且没给 `overwrite`。
     上限 2 万个文件、解开后 4 GiB。
   - **与方案的偏差。** “逐个核对 sha256”做成了：回复里逐个列出解开的文件和 sha256（前 200 个），由上传方对照；zip 里每个文件的 CRC-32 在解开时自动核对；整包仍可用 `sha256=` 核对。没有另收一份清单。
2. **大文件分片**：
   - `fs_upload_url(size=字节数)` 超过 `part_mb`（默认 4 MB，最大 64）时，每片一个链接，最多 128 片、共 2 GB。
   - 分片写进目标旁边的暂存文件，可以乱序、并行。长度不对的片回 400，可以对同一个链接重传。
   - 全部到齐后核对整个文件的 sha256：不对就清空已收记录，可以重传；对了再移到目标位置，或者解开。
   - 每到一片，所有分片链接的有效期都顺延；过期仍未传完的，删掉暂存文件。
   - 不用改中转：每片就是一个普通的一次性链接。
3. **暂存目录**：
   - 默认 `~/.winhand/scratch`，`config.toml` 的 `[scratch] folder` 可以改。
   - `context()` 给出路径；winhand 启动的程序有 `WINHAND_SCRATCH` 环境变量。
   - 不自动清理，等用户决定。
4. **一次处理多个文件**：
   - `fs_read(paths=[…])`：最多 20 个，字数上限平分；文档给正文，图片提示单独读。守卫按读每个文件判断。
   - `fs_edit(files=[…])`：
     - 每个文件的修改先在内存里算好，有一处对不上就一个文件也不写。
     - 写到中途失败（比如文件被别的程序占着）时，把已经写过的文件还原。
     - 同一个文件出现两次，按顺序合并成一次。
     - `dry_run=true` 只给差异，不写，守卫按读判断。
     - 主人的 Codex / Claude Code hooks 看到的是每个文件各自的修改。
   - **与方案的偏差。** `fs_search` 一次多个查询没做。0.8.0 起它标了只读，Claude Code 会把同一轮里的几个调用并行执行，再做一个参数省下的只是几次往返。
5. **原文对不上时**：给出最接近的原文、相似度和差异；新内容里出现文件原来没有的 `\"` 时提醒。
6. **`context()`**：
   - `brief=true`：技能只列名字，规矩和守卫照旧给全。
   - 每次回答带 `digest`；`since=digest` 时，内容没变就只回 `unchanged`。回答里提醒：上次的回答已经被压缩掉的话，不要带 `since`。
7. **`remote_run` 补齐**：
   - 加 `secrets=`；Python 脚本也拿得到 `env` 和 `cwd`。
   - 新工具 `remote_copy`：经 scp 传文件或文件夹，上传或下载。
   - 结果里网址中的 `user:password@` 一律遮挡。
   - `run` 直接调 ssh、scp 时，回复里附 `hint_ssh`。
   - **与方案的偏差。** 端口转发没有加新工具。复盘里 AI 已经用 `job_start(ssh -N -L …)` 做到了；`help()` 和 ssh 提示里给出写法（带 `ExitOnForwardFailure`），用 `job_stop` 关闭。
8. 开场说明已有 4091 字（上限 4096），这轮没加内容；新功能写进 `help()`、工具说明和 README。

  - `fs_edit` 对不上时给最接近的原文；多出的 `\"`；
  - `fs_read(paths)`：文本、文档、图片、不存在的文件，以及守卫按读每个文件判断；
  - 文件夹下载：zip 内容、压缩方式、`include`/`exclude`、读规则排除的文件、链接不跟进去、打包途中消失的文件；
  - 上传解开：zip、覆盖、7 种不安全的名字、tar、tar 里的链接、大小写撞名、写规则、经已有链接写到外面；
  - 分片：乱序、长度不对时重传、整文件 sha256、暂存文件清掉、分片后解开、过期时删掉暂存文件；
  - `context` 的 `brief`、`digest`、`since`，以及暂存目录；
  - `fs_edit(files)`：预演、有一处失败就全不写、同一文件合并、写到中途失败时还原、hooks 看到各自的修改。
- **修了第 2 轮的一个测试**：`test_a_long_wait_ends_when_the_job_goes_quiet_without_cpu` 在整套测试的负载下偶尔失败。
  - 原因：建客户端花的时间超过了 1 秒的卡住阈值，等待开始时任务已经算卡住了。按设计，这不算新情况，于是等满了 30 秒。

- **CI 的 Windows 任务**（run 41237721014）：829 个里 2 个失败，都是测试本身的问题：`write_text` 在 Windows 上把 `\n` 写成 `\r\n`，zip 里如实带着 `\r\n`，还原写回的也是原样的 `one\r\r\n`。测试改成写字节，随第 4 轮的提交一起修。
- **还没做（需要用户配合）**：
  - 在 Windows 上实测：长路径、联接点、文件被占用时的打包和解开；经中转的分片上传，每片能否在沙箱的约 30 秒内传完。用到链接的测试在 Windows 上跳过，其余由 CI 的 Windows 任务跑。
  - 这轮不改中转。

## 实测（2026-11-01，0.10.0 装在用户电脑上；从云端沙箱经中转传）

- **单个小文件上传**：200，0.8 秒，sha256 一致。
- **10 MB 分片上传**（照 `fs_upload_url(size=…)` 给的 curl 写法）：3 片分别 7.7 秒、6.1 秒、2.5 秒，最后一片回复整个文件的 sha256，与本地一致。
- **对照：25 MB 一次传完**：200，17.4 秒，没有出现复盘里约 30 秒就 502 的情况。今天的网速大约 1.4 MB/s，分片在更慢的网络或更大的文件上才用得着。
- **文件夹下载**（`include=["*.py","*.txt"]`）：zip 校验通过，2 个文件的 sha256 与原文件一致。
- **上传后解开**：3 个文件（含子目录和中文名）全部解开，逐个列出的 sha256 与打包前一致。
- **`fs_read(paths)`**：两个文件正常读出，不存在的那个单独报错。
- **`context(brief=true)`**：技能只列名字，带 `digest` 和暂存目录。
- 测试留下的文件在 `~/.winhand/scratch/tests/`，没有删。
