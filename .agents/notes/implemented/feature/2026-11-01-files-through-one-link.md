# Agent Note: 多个文件和大文件经一次性链接进出电脑

Status: implemented

## Problem

2026-11-01 的使用复盘（`docs/reviews/2026-11-01-usage-review.md`）里，文件进出电脑有三处绕路：

- 57 批一次传 4 个以上的文件，共 349 个，几乎都是先用命令打 zip，另一头再手动解开。
- 超过约 8–10 MB 的单次上传，有的沙箱约 30 秒就返回 502，文件其实传到了。AI 于是改成 4 MB 切片：一个文件 35 次上传、34 次删除，约 17 分钟。
- `%TEMP%` 被手动清理过两次，暂存在里面的文件跟着丢了。

不改的话，每批文件都要 AI 在两头手写打包、切片、拼接的脚本，多出几次调用，也多出几次出错的机会。

## Decision

- **文件夹下载边打包边下载。** `fs_download_url(path=文件夹 | paths=[…], include, exclude)` 签发链接时就定下文件清单（`bundle.plan_download`）；有人下载时才打包，边打包边发（`bundle.stream_zip`：zipfile 写进不能 seek 的流，每个文件的大小写在数据之后）。电脑上不落临时 zip，所以回复里没有 sha256，改为提示用 `unzip -t` 检查。
- **逐个文件过读规则。** `guard.PathCheck("read", …)` 与 `fs_search` 的结果过滤共用同一段代码。逐个文件时没人可问，`ask` 也算拒。被挡的文件不放进 zip，回复里列出名字。链接和联接点不跟进去。
- **上传解开全有或全无。** `fs_upload_url(path=文件夹, extract=true)` 在写第一个文件之前查完：名字安全；包里没有链接和设备文件；经文件夹里已有的链接不会写到外面（文件夹条目也查）；在 Windows 上不撞名；写规则（`PathCheck("write", …)`，含桌面审批文件）；已存在的文件（没给 `overwrite`）。有一项不过就整包拒收。每个文件先写临时名，再用 `fs.replace_with` 换上。
- **分片每片一个普通的一次性链接。** `fs_upload_url(size=…, part_mb=4)` 给出最多 128 个链接，令牌仍是 43 个字符，中转的 `/t/<token>` 路由不变。
  - 所有片写进目标旁边的同一个暂存文件 `.<名>.upload-<id>.parts`：放在同一个目录，最后才能原子地换上。
  - 片可以乱序、并行；整个文件完成之前，一片可以重传。
  - 到齐后核对整个文件的 sha256。
  - 每到一片，所有片的有效期一起顺延；过期仍未传完的，`transfer._sweep` 删掉那一个暂存文件。
- **暂存目录。** `config.scratch_dir()`，默认 `~/.winhand/scratch`，`config.toml` 的 `[scratch] folder` 可改；`WINHAND_SCRATCH` 环境变量交给 winhand 启动的程序。不自动清理。

## 链接的回复格式

- 分片：每片回 `{"ok": true, "part": i, "received": k, "parts": n}`。最后一片回 `{"ok": true, "done": true, "path", "bytes", "sha256"}`，带 `extract` 时回解开的结果。长度不对回 400；整个文件的 sha256 不对回 422，并清空已收的记录，可以重传。
- 解开：成功回 `folder`、`files`、`bytes`、`listing`（最多 200 个 `{path, bytes, sha256}`）、`archive_sha256`、`archive_bytes`；拒收回 422，`error` 里写明 `nothing was unpacked` 和挡路的名字。
- 下载的 zip：名字从所有给定路径的共同上级开始，所以单个文件夹解开就是它自己。

## Alternatives considered

- **签发时先在电脑上建好 zip，再按单个文件下载。** 最强的理由：回复里能给出 size 和 sha256，与单个文件的下载一致。否掉的原因：大文件夹打包可能超过一次调用的时间；电脑上要放临时 zip，就得有人清理，清理就是程序批量删除用户磁盘上的文件，而暂存清理本身还在等用户拍板。边打包边下载什么都不落盘。
- **改中转，让一个令牌带片号（`/t/<token>/<n>`）。** 最强的理由：回复里只有一个链接，curl 循环更短。否掉的原因：电脑端和中转要一起部署才能用，只装了一边就是 404。每片一个链接不用动中转，代价只是回复里多几行链接。
- **单次上传报 502 时，让 AI 自己用 `fs_stat` 核对。** 最强的理由：一行代码都不用改，文件其实传到了。否掉的原因：AI 看到 502 会先当失败处理，复盘里正是这样才改成了切片；而且多久报错取决于沙箱，不可靠。
- **解开时跳过受保护或已存在的文件，其余照写。** 最强的理由：一个文件挡路，不至于整包作废。否掉的原因：只写了一部分，AI 很难察觉缺了什么。全有或全无时，回复点名挡路的文件，重新打包即可。下载方向则选“留出不放”：少给文件不会改动电脑。
- **暂存目录定期清理 7 天前的文件。** 最强的理由：不会越攒越大。暂不做：这是程序批量删除用户磁盘上的文件，要等用户同意（复盘第八节第 3 问）。

## Consequences

- **收益**：
  - 一批文件一次调用、一个链接；
  - 大文件的每一片都在沙箱的时限之内；
  - 解开不会写到目标文件夹外面，也不会因为撞名互相覆盖；
  - 搜索、下载、解开三处逐个文件的规则判断是同一段代码。
- **代价与已知上限**：
  - 下载的 zip 没有事先的 sha256，只能靠 zip 里每个文件的 CRC-32。
  - 逐个文件时 `ask` 一律算拒。用户在调用这一级点了允许，文件夹里同一条 `ask` 规则覆盖的文件仍会被留出，与 `fs_search` 相同。用户为此抱怨时，要把调用级的同意传给 `PathCheck`。
  - winhand 在分片上传中途重启：令牌只在内存里，暂存文件会留在目标旁边，没有自动清理。
  - 主人的 Codex / Claude Code hooks 只在签发链接时按目标文件夹跑一次，解开时不逐个文件跑。
  - 上限：解开 2 万个文件、4 GiB；分片最多 128 片、共 2 GB，单片最大 64 MB。
